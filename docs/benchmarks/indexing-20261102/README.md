# 索引性能：2026-11-02

本次优化处理三个已复现的瓶颈：整本 OCR 任务独占后台通道、短页 embedding 批次过碎、逐条持久化和重复页内容写入。原始数据为 [改前](./before.json)、[改后](./after.json)，源码哈希和限制见 [provenance.json](./provenance.json)。两版均为未提交工作树，不代表 npm 发布版本。

## 测量方法

Apple M5 Pro、macOS arm64、Node 26.7.0。每组 3 次，表中为中位数。固定 1024 维假向量、相同文字和位置数据、8 MiB 序列化热缓存；用真实临时目录执行持久化、关闭并重新创建服务。模型没有延迟，不调用网络、OCR 或 PDFium；未清空 OS 文件缓存。计时包括分块、校验、序列化和持久化。

```sh
npm run bench:indexing -- /tmp/pdf-indexing.json
```

## 实现与边界

- 后台单通道按有界步骤轮转。750 ms 是软期限，正在执行的 OCR／网络调用会完成或取消后才让位；手动优先有次数限制，避免其他文档饥饿。
- 跨页批次最多 16 个输入，保留引擎更小上限；窗口最多 16 页、约 8 MiB 软上限，仍受工作内存硬预算限制。相同文字合并，不为填满批次重复计算。
- SQLite WAL／FULL 批量提交；向量先落盘，页头随后发布。V2 内容和位置不可变，向量使用独立模型／文字键，检查点只引用它们。旧 JSON 自动迁移，失败和取消后续建。
- 重启先恢复页头与有效向量；查询使用前完整验证内容和位置。SQLite 页缓存额外限 8 MiB，mmap 关闭；这不是全进程内存上限。
- 元数据成功缓存 2 秒并合并并发请求，凭据或配置改变会隔离，响应仍检查模型代次。PDFium 串行锁不再包含 PNG 压缩；没有默认并发调用可能共享 GPU 的 OCR、描述和 embedding 引擎。
- 诊断按运行尝试汇总原生提取、渲染、PNG、OCR、描述、embedding 和存储阶段，记录累计活跃步骤时间。阶段可能嵌套，不能相加当作总时间；仅记录时长、次数和有界错误信息。

## 验证场景

真实 SQLite 测试包含事务中途失败回滚、SIGKILL 后恢复、旧 JSON／StorageDomain 迁移、跨实例清空防复活、损坏与缺失、热缓存边界。核心测试覆盖批处理去重、失败与取消后续建、轻量重启恢复及授权围栏；调度测试覆盖让位、有限优先与旧时间片回调。原生测试验证慢 PNG 编码不会阻塞下一次读取或文档释放；浏览器验证进度、取消、续建和跨会话复用。

后续真实耗时若仍以 OCR／视觉模型为主，应依据新阶段日志评估引擎吞吐、模型选择和服务延迟。此基准不衡量检索质量，也未改变 OCR／图像描述的覆盖策略。
